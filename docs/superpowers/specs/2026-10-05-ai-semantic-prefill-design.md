# AI 记账完整预填与摘要复核设计

日期：2026-10-05。交付状态：用户已指示开始实施。API v2 语义提取、Flutter 语义草稿和摘要复核已完成自动化验证；真实供应商评测和生产发布未执行。

## 1. 产品目标与范围

一句自然语言生成完整、可核对的记账结果。信息明确时，用户只需一次确认；出现歧义时，仅补充相应字段。

用户原话：

> 张三在昨天住宿花了400元，他垫付的，所有人都用上了。

第一版包括：账本上下文、相对日期锚点、句内指代、付款模式、全体及排除人员语义、现有分类匹配、简洁备注、摘要复核、按字段处理歧义、多笔草稿总览、旧草稿兼容。

第一版继续使用现有交易模型和均摊逻辑。支持文字以及语音转写后的文字；不新增音频接口、供应商、数据库表或管理员页面。

实际支持非均等分摊和多人付款仍属后续迭代；本期必须识别这类描述并阻止其静默套用均摊或单一付款人。其他后续迭代包括：用户可管理的人员别名及分类映射记忆、跨次输入的聊天补充、批量确认、截图及账单导入、疑似重复交易匹配、跨账本路由。本期不依赖这些后续功能才能完成核心示例。

## 2. 已确认的现状

评审基线：Flutter `3c3993e`；API `b9c78cb`。以下结论来自源代码与现有测试，未使用真实供应商测量识别准确率。

| 现状 | 产品影响 |
| --- | --- |
| `DeepSeekDraftClient.parse` 只接收文字、时区及默认币种 | 没有账本人员、分类候选和明确参考日期 |
| 模型结果只有 `payerName` 和 `personNames` | 无法明确表达全体、排除范围、未知付款方式 |
| `AiDraftValidator.resolve` 使用唯一姓名匹配及“我” | 名称唯一匹配可靠，但未识别角色合并到了 `unresolvedNames` |
| 分类由本机偏好精确匹配 | “住宿”与默认“居住”不一致时无法预选 |
| `AiDraftReview` 用空付款人显示共同钱包 | 未知付款与共同钱包混淆 |
| 缺少日期时，保存使用 `DateTime.now()` | 草稿隔天确认可能改变发生日期 |
| 队列、权限检查、稳定操作 ID 已存在 | 可继续复用恢复和幂等保存能力 |

## 3. 核心示例的确定结果

固定测试上下文：当地日期 2026-10-05，`Asia/Shanghai`，币种 CNY，账本人员 `[张三、李四、王五、赵六]`，全部有效，张三姓名唯一。

| 字段 | 结果 | 依据 |
| --- | --- | --- |
| 收支类型 | 支出 | 原文“花了” |
| 金额 | 400.00 | 原文金额 |
| 币种 | CNY | 原文“元” |
| 日期 | 2026-10-04 | 原文“昨天”及服务端参考日期 |
| 日期精度 | DAY | 没有具体时刻；摘要不显示 00:00 |
| 付款模式 | PERSON_PAID | 原文“垫付” |
| 付款人 | 张三的有效 UUID | “他”指向同句唯一的张三 |
| 承担人员 | 四位人员的 UUID 快照 | 原文“所有人” |
| 分摊 | EQUAL | 现有产品默认均摊；标注“默认均摊” |
| 分类 | 优先已有“住宿”；仅有“居住”时建议“居住” | 候选分类及内置语义映射 |
| 备注 | 住宿费用 | 对原文事项的简洁整理 |

“所有人都用上了”说明承担人员范围，均摊来自产品默认行为，不能把二者的证据合并。“他垫付”说明张三支付资金，不说明张三是否参与承担；本例由“所有人”单独决定包含张三。

如果唯一分类为“居住”，卡片展示“居住 · 根据住宿建议”，用户确认本笔即可；系统不偷偷创建“住宿”，也不在本期记住用户的映射选择。存在“住宿”时直接选“住宿”。存在多个同等合理候选且没有明确依据时，要求选择分类。

## 4. 流程与责任分工

```mermaid
flowchart LR
    A[文字或可编辑转写] --> B[权限与输入校验]
    B --> C[构造账本上下文]
    C --> D[一次模型调用：提取语义]
    D --> E[格式校验与账本映射]
    E --> F[保存本机草稿]
    F --> G[多笔总览与摘要复核]
    G --> H[用户补充或局部修改]
    H --> G
    G --> I[保存前检查当前数据]
    I --> J[既有交易保存与同步]
```

- API 提供有效人员、账本名称和币种，负责 UUID 映射；模型只提取姓名与范围，不能指定 UUID。
- Flutter 提供本机真实分类候选。分类是可编辑选项，不构成账本权限或资产数据。
- 服务端用系统时钟和请求时区计算参考日期。模型输出的日期继续被校验。
- 模型调用每次输入一次，不为每个字段或每笔草稿重复请求。
- Flutter 负责草稿编辑、补充问题、恢复及确认。解析接口继续只生成草稿。

## 5. 上下文与接口版本

保留 `/api/ledgers/{ledgerUuid}/ai-bookkeeping/parse` 路径。

### 5.1 新请求

```json
{
  "text": "张三在昨天住宿花了400元，他垫付的，所有人都用上了。",
  "zone": "Asia/Shanghai",
  "schemaVersion": 2,
  "expenseCategories": ["默认", "交通", "餐饮", "居住"],
  "incomeCategories": ["默认", "工资", "其他"]
}
```

- `schemaVersion` 缺省为 1；只接受 1 和 2。
- 保持输入 1–1000 字、单次 1–10 笔限制。
- 分类列表允许省略，每类最多 100 项、单项最多 64 个 Unicode 字符；去空白、去重复。分类候选作为数据序列化，不拼接成指令。省略候选的 v2 请求不强行填“默认”，分类进入待选择状态。
- 时区继续支持合法 IANA 标识及客户端当前 UTC 偏移。
- 分类选择器加载完成后才能发送 v2 请求，避免本机自定义分类未加载时被判为不存在。
- 账本与人员由服务端鉴权后读取，客户端不能提交权威人员 UUID 或人员范围。
- 有效人员不能静默截断：本期 v2 上下文最多 100 人；超过时保留输入，提示本期不支持该规模的 AI 人员匹配，并提供手动记账入口。
- 客户端和服务端各自校验请求；服务端是最终检查方。

### 5.2 能力协商

`capability` 增加 `draftSchemaVersion: 2`。新客户端遇到字段缺省时视为 1，使用旧解析请求和详细复核，并显示信息需要人工核对。保留原有 `textAvailable`、`voiceAvailable` 和 `reason`。

旧客户端继续发送 v1 请求，走既有供应商方法和校验方法。v2 新字段不改变 v1 必填字段与响应 `entries` 封装。先部署后端，再部署支持 v2 的客户端。

### 5.3 发给模型的必要上下文

JSON 数据包含：账本名称、默认币种、支持币种、参考日期、请求时区、有效人员姓名及 `isSelf` 标志、现有收支分类候选、固定默认均摊规则和本次原文。

本期不发送账号联系方式、历史流水、完整成员账号资料。不同账本独立取候选；用户提到其他账本时不自动路由，显示当前作用范围并由用户重新选择账本。

## 6. 模型语义结构与响应

### 6.1 模型原始条目

```json
{
  "sourceText": "张三在昨天住宿花了400元，他垫付的，所有人都用上了。",
  "type": 0,
  "amount": "400.00",
  "amountExpression": "400",
  "currencyCode": "CNY",
  "categorySuggestion": "住宿",
  "note": "住宿费用",
  "dateExpression": "昨天",
  "happenedAt": null,
  "paymentMode": "PERSON_PAID",
  "payerName": "张三",
  "participantScope": "ALL",
  "personNames": [],
  "excludedPersonNames": [],
  "splitMode": "EQUAL"
}
```

枚举：

- `paymentMode`：`PERSON_PAID`、`SHARED_POOL`、`UNKNOWN`。收入条目不使用付款模式，客户端隐藏对应区域。
- `participantScope`：`ALL`、`SPECIFIED`、`UNKNOWN`。全体排除若干人用 `ALL + excludedPersonNames` 表达。
- `splitMode`：`EQUAL`、`UNSUPPORTED`、`UNKNOWN`。未说明份额时可以使用默认 `EQUAL`；明确非均等份额、多付款人时必须提出不支持提示，不能丢弃份额信息后均摊。

`sourceText` 必须是原输入中的完整、连续片段。模型不得编写原文、酒店名称、人数、时间或其他未出现的事实。`payerName` 与具名参与人须使用原输入中实际出现的名称；“我”由账号绑定映射，句内“他”可还原为原文明确出现的唯一先行姓名。“小张”不能在没有别名规则时自动改成“张三”。

保留已有金额、类型和币种的强校验。增加 `amountExpression` 作为原文金额片段，必须真实存在于本笔 sourceText 中，并能确定性转换为与 amount 相同的金额。支持阿拉伯数、千位分隔、中文整数和“点”小数；原文中的金额表达无法校验时明确提示用户用数字补充，不能靠模型猜测。

本期不新增无金额草稿：任一条目缺少有效金额、金额证据或类型时，整个请求明确报错并保留原输入，不输出虚构金额、不静默丢笔。姓名、分类、日期及付款模式的歧义则保留可解析草稿，以字段问题表示。

### 6.2 客户端条目

```json
{
  "schemaVersion": 2,
  "sourceText": "张三在昨天住宿花了400元，他垫付的，所有人都用上了。",
  "type": 0,
  "amount": 400.00,
  "currencyCode": "CNY",
  "categorySuggestion": "居住",
  "categoryOriginalSuggestion": "住宿",
  "note": "住宿费用",
  "happenedAt": "2026-10-04T00:00:00",
  "datePrecision": "DAY",
  "referenceDate": "2026-10-05",
  "referenceZone": "Asia/Shanghai",
  "paymentMode": "PERSON_PAID",
  "payerPersonUuid": "p-zhang",
  "participantScope": "ALL",
  "personUuids": ["p-zhang", "p-li", "p-wang", "p-zhao"],
  "splitMode": "EQUAL",
  "fieldSources": {
    "happenedAt": "EXPLICIT",
    "paymentMode": "EXPLICIT",
    "payer": "EXPLICIT",
    "participants": "EXPLICIT",
    "category": "SUGGESTED",
    "splitMode": "DEFAULT",
    "note": "SUGGESTED"
  },
  "issues": [],
  "unresolvedNames": []
}
```

`fieldSources` 值为 `EXPLICIT`、`DEFAULT`、`SUGGESTED`、`USER`，由服务端匹配结果或用户编辑生成，不采用模型自报的百分比可信度。`DEFAULT` 表示产品默认，`SUGGESTED` 表示可修改建议。`categoryOriginalSuggestion` 保留匹配前事项分类，供展示“住宿 → 居住”。`unresolvedNames` 保留给旧协议；v2 使用按角色划分的 `issues`。

新 DTO 字段均为增量字段。`happenedAt` 继续使用现有本地日期时间契约，`datePrecision=DAY` 时仅展示日期；存储的 00:00 是日期载体，不展示为用户说出的具体时间。本期沿用既有交易时间存储约定，不增加跨时区交易时间迁移。

### 6.3 问题对象

```json
{
  "id": "payer:PERSON_AMBIGUOUS:张三",
  "field": "payer",
  "code": "PERSON_AMBIGUOUS",
  "sourceText": "张三",
  "candidateUuids": ["p-zhang-a", "p-zhang-b"]
}
```

`field` 为 `paymentMode`、`payer`、`participants`、`excludedParticipants`、`category`、`currencyCode`、`happenedAt`、`splitMode` 或 `legacy`。同名出现在付款和承担两处时分别生成问题，不能因选择付款人而自动消除参与人问题。

固定问题码：`PAYMENT_UNSPECIFIED`、`PERSON_NOT_FOUND`、`PERSON_AMBIGUOUS`、`PARTICIPANTS_UNSPECIFIED`、`CATEGORY_UNMATCHED`、`DATE_AMBIGUOUS`、`DATE_INVALID`、`CURRENCY_UNSUPPORTED`、`UNSUPPORTED_SPLIT`、`CONFLICTING_FIELDS`、`LEGACY_REVIEW_REQUIRED`。展示文案来自客户端固定映射，不直接使用供应商自由文本。

## 7. 具体匹配规则

### 7.1 付款与人员

1. “张三垫付/张三代付/张三先出的/张三买单”提取个人付款；姓名唯一匹配时填对应付款人。
2. “共同钱包/公款/公共资金支付”提取共同钱包。`SHARED_POOL` 必须有明确证据或用户显式选择。
3. “张三住宿花了400”可以确定支出事项，但缺少充分付款方式信息时 `UNKNOWN`；不因出现姓名就自动认定垫付。
4. “我”只在当前用户绑定的有效记账人员唯一时匹配；不能用第一位人员代替。
5. 句内“他/她”只有唯一明确先行人时还原；多个候选或跨次输入的指代进入待确认。
6. `ALL` 展开当前账本有效 `LedgerPerson`，记录真实 UUID 快照；全体包括付款人，除非明确排除。
7. “所有人除了李四”先展开全体，再移除唯一匹配的李四。排除对象不明确时提出问题，必须解决后才能保存。
8. `SPECIFIED` 只使用原文明示人员；付款人不自动加入承担人员。付款人可以不承担费用。
9. “我们三个人/他们几个”而没有可唯一确定的名单时要求选择人员；数量一致不足以证明具体名单。
10. 无参与人员范围时要求选择；不自动全选。不根据用户常用人员推断。
11. 付款信息互相矛盾时生成冲突问题；不以最后一个词覆盖前面的付款信息。

服务端对原文片段、姓名出现位置、全体证据及付款模式证据做一致性检查。检查可以发现明显矛盾，但不能替代真实模型评测与用户核对。

### 7.2 分类

按收支类型选择候选列表；明确现有分类优先，其次使用内置语义组建议，再要求用户选择。

| 语义组 | 原文示例 | 候选优先级 |
| --- | --- | --- |
| 住宿 | 住宿、酒店、宾馆、房费、住店 | 住宿，其次居住 |
| 餐饮 | 早餐、午餐、晚餐、吃饭、聚餐 | 餐饮 |
| 交通 | 打车、出租车、公交、地铁 | 交通 |
| 工资收入 | 工资、薪资 | 工资 |

只填真实存在且类型正确的分类。模型给出的其他现有分类可以作为建议；例如用户自定义“差旅”仍可由模型选中。候选歧义或不存在时，展示原始建议并允许选择或明确新增。空建议不自动落入“默认”。

### 7.3 日期

- 服务端在请求时捕获一次参考日期，单个批次全部条目使用同一锚点。
- 确定性解析“今天、昨天、前天、昨晚、上周一至上周日”和 ISO 日期；“上周”指参考日期之前的完整自然周，周一为周起始。
- 原文有明确日期但解析不了时生成日期问题；不能改成今天。
- 原文没有日期时填参考日期，并标注“今天（默认）”。草稿翌日恢复仍显示原来的具体日期。
- 只提到日期时精度 DAY；原文明确时刻且结果合法时精度 TIME。原文无时刻不得凭模型输出填具体钟点。
- 未来日期或非法当地时间进入日期问题，保留其他字段，不自动退回今天。
- 本期新增日期解析对 v2 生效，v1 路径仍保持供应商契约。

### 7.4 备注与分摊

备注简洁描述事项，保留“含早餐、停车费、押金”等原文附加信息，不重复拼接金额、日期和全部人员。未提供酒店或商户名称时不得补写。原文单独保留，可展开查看。

未说明不同份额时按当前交易能力均摊，标注默认。明确“张三300、李四100”“按比例分”“两个人分别付款”时标记 `UNSUPPORTED_SPLIT`，允许回到输入重新表达支持的记录，或用户明确修改成均摊；不能直接确认原来的复杂分摊。相关提示须出现在本笔而非被隐藏到备注。

## 8. 复核交互

### 8.1 完整草稿

```text
AI 记账 · 当前账本                    第 1/3 笔

居住 · 支出 CNY 400.00
2026-10-04 · 张三垫付
全体 4 人承担 · 默认均摊 CNY 100.00/人
分类：根据“住宿”建议为“居住”
备注：住宿费用

日期   分类   付款人   承担人员   金额   备注  [可点击编辑]
查看原文 / 展开全部字段

稍后处理                              确认记账
```

默认摘要可在常见手机屏幕内看清核心结果和确认操作；具体日期总是显示，不只显示“昨天”。全体人数可以展开名单。

点击字段打开复用的日期、分类或人员控件，只编辑该字段；完整分组表单作为“展开全部字段”继续保留。修正付款人不会自动改变承担人员。修改收支类型时清除不适用的付款字段并重新校验分类。

### 8.2 待补充草稿

显示摘要以及固定的待补充问题列表。点击问题仅展开对应字段；不会要求用户再次填写已确定金额和备注。未解决的问题阻止确认，并显示“还有 N 项待确认”。

- 付款人问题：只能选择有效付款人，或显式切换为共同钱包；没有泛化的“忽略付款人”操作。
- 指定参与人问题：选择对应人，或明确“不计入本笔”，仅影响该角色。
- 排除人员问题：选择需要排除的人，或明确取消这项排除；修改后保留快照并复查人数。
- 未支持的分摊：解释当前能力；用户明确选择均摊后更新为 USER 来源并清除对应问题。
- 无参与人、分类失效、人员失效等本机检查生成动态问题；不能只看服务端返回的问题列表。

### 8.3 多笔与草稿状态

生成多笔后显示紧凑总览，包含原顺序、事项、金额、状态。可以点选任意草稿复核；默认选首个未完成条目，保持原批次 `position/total`。

状态为“可确认”“待补充”“保存中”“已确认”“保存失败”。已确认条目从待办移除，退出提示保持当前确认、跳过和剩余计数。第一版仅逐笔确认；批量确认独立迭代。

切换草稿前等待当前编辑持久化完成；保存后先找下一条，当前条目失败时仍保留并显示错误。不存在当前条目时选择剩余首条；不通过改变队列顺序模拟切换。

## 9. 编辑、恢复与保存

- 增量字段写入现有 `AiDraft.toJson/fromJson`；队列外层 `version=1`、UUID、operationId、position、total 不变。
- 保存语义字段、来源、问题、参考日期及当前已解析名单；不保留原始音频。
- 编辑金额为非数字时，继续使用现有 `amountInput` 保存原始输入；摘要不得显示旧的有效金额冒充当前输入。
- 保存前重读账本权限、有效人员、本机当前分类、支持币种；检查收支类型、正金额、日期、付款模式、均摊模式及未解决问题。
- `PERSON_PAID` 必须存在有效付款人；`SHARED_POOL` 必须明确选择且付款人为空；`UNKNOWN` 不能保存支出。
- `personUuids` 非空且全部有效。新增人员不自动加入旧的 ALL 草稿；删除已选人员产生问题，不静默移除。
- 编辑承担人员后 `participantScope=SPECIFIED`、来源 USER；不再显示“全体”。
- 确认时沿用 `_saveAiDraft → transactionProvider.addTransaction`，稳定交易 UUID 与 clientOperationId 不变。
- 在支付模式和问题检查通过后，转换成既有交易模型：PERSON_PAID 对应非空 payerPersonUuid，SHARED_POOL 对应空 payerPersonUuid。

## 10. 兼容、失败与发布

### 10.1 旧本机草稿

`schemaVersion` 缺省为 1。非空有效付款人可以迁移为 PERSON_PAID；空付款人迁移为 UNKNOWN，要求明确选择模式。不能把旧空值假定为共同钱包。

旧 `unresolvedNames` 已丢失角色信息，不冒充 v2 按角色问题。显示 `LEGACY_REVIEW_REQUIRED`，进入既有详细复核，要求用户核对付款人与承担人员；用户完成确认后产生明确模式和角色结果。旧草稿不重分配交易或操作 ID，不自动重新调用模型。

### 10.2 故障与权限

供应商超时、限流、响应格式错误、非法金额、超出条数：保留输入，明确失败原因，允许重试或手动填写；不会生成虚假“成功”草稿。授权与账本权限继续在请求时校验。

字段歧义：保留草稿，逐字段处理。确认前发现权限或人员变化：阻止保存并保留编辑；此前已成功保存的交易继续有效。

### 10.3 发布与回退

1. 发布支持 v1/v2 的 API，确保旧客户端的文本和语音流程继续运行。
2. 发布通过能力协商启用 v2 的 Flutter 客户端。
3. 小范围进行真实中文样例评测，检查完整预填与角色错误。
4. 出现协议级问题时暂将能力协商降为 1，新客户端走详细复核；不能借降级消除旧草稿里的待确认问题。

## 12. 指标与通过条件

- 核心 A01–A06、A09、A16–A18、A21 的无歧义固定样例，映射和 UI 测试全部通过。
- 所有歧义、失效人员、未知模式和不支持分摊测试都无法静默确认。
- 真实模型评测分别记录：完整预填率、整笔完全正确率、无需修改确认率、付款人/模式错误率、承担名单错误率、平均修改字段数、确认操作次数和解析耗时。
- 首轮至少 60 条语料，每条真实模型运行 3 次，保留失败分类。建议无歧义样例的整笔完全正确率达到 90% 后再扩大试用；这是验收目标，不是现有实测结果。
- “可确认”意味着结构检查通过，仍需用户确认；不能把它命名为“已核实”或“保证正确”。
- 摘要均摊金额是现有逻辑预览，不新增尾差分配算法。不能整除时显示“约每人”，不得承诺各份额严格相加等于总额。
