# AI 记账语义匹配与草稿确认设计

日期：2026-10-02

## 目标和范围

用户已同意改善人员匹配与金额确认，并补充要求：将现有分类提供给 AI，根据语义选择分类。
本设计覆盖 Flutter 客户端和 API，不涉及 Admin 改动、授权策略变化、自动保存交易或自动创建人员/分类。
本文件用于实施前确认；尚未修改功能代码。

## 当前实现问题

- API 只按人员姓名完全相等匹配，或者将“我”映射到当前账号关联人员。
- AI 请求只有描述、时区和币种，没有当前账本有效人员和现有分类上下文。
- API 返回云端人员 UUID，草稿确认直接与本地 UUID 比较，未处理同步身份映射。
- 分类来自客户端 `TransactionCategoryPreference`，包含默认分类和自定义分类，收入、支出分别存储。API 不掌握该列表。
- 草稿未确认付款方式时以空付款人表示，界面直接解释为共同钱包；未选承担人仍显示“0 人承担”和空白每人金额。
- 原币金额与换算金额使用同等视觉层级，币种标识重复；异常匹配提示被用作下拉框标签，容易截断。

## 选定方案

采用“AI 语义理解 + 服务端约束校验 + 客户端显式确认”的混合方案。
仅靠字符串规则难以理解口语；完全信任 AI 可能生成不存在的人员或分类。
AI 输出只作为可编辑草稿，确认前不写交易。

## 人员匹配

1. API 鉴权后读取当前账本未删除的人员，提供必要的姓名上下文给 AI；不使用其他账本或账号人员，不提供手机号、密钥等无关资料。
2. 保留用户原始姓名表达，优先完全同名，再考虑称呼、同音和近似字。不得把姓名近似直接当成人员已删除。
3. “我”仅通过当前登录账号与账本人员的关联确定；没有关联时待确认，不按显示名或第一位人员猜测。
4. 完全同名唯一时直接填入；近似自动预填限定为规范化后的完整姓名拼音（不计声调）相同且候选唯一，展示原表达、匹配姓名及“近似匹配，可修改”。规范化包括去首尾空白和统一全角/半角，不去掉姓氏。
5. 同名、多候选或弱匹配时展示候选人员供用户选择，禁止随机选一个。AI 自报置信度不能单独作为自动匹配依据。
6. 同音候选按完整拼音比较；近似字候选使用长度至少为 2 且相差最多一个字的姓名比较。后者以及简称、称呼只提供候选、不自动预填；不能仅因只有一位候选就绕过歧义检查。多音字产生多个拼音解释时仍须检查全部候选，规则应可重复测试。
7. 匹配结果保留原表达和匹配来源，承担人与付款人的待确认状态分别处理。
8. 客户端将返回的云端人员 UUID 转换为当前账号本地 UUID，再加入草稿队列。恢复旧草稿时同样处理映射，转换应幂等。
9. 真正不存在或已删除的人员明确提示“这位人员当前不在账本中，请重新选择”；不得显示“原参与人已失效 1”这样的内部占位名。

## 分类语义选择

1. 每次生成草稿前，客户端读取当前有效的收入、支出分类列表，包含默认分类和所有自定义分类，去空白、去重后随请求发送。
2. 分类列表作为数据传给 AI，不作为额外指令；分类顺序和最近使用顺序不得影响语义判断。
3. AI 先判断收入或支出，再仅从对应列表中选择最贴切的分类。用户明确指定了有效分类时优先遵从；存在更贴切的自定义分类时可选择该分类。
4. 默认分类下：早餐、午餐、晚餐、零食归“餐饮”；打车、地铁归“交通”。这些是语义示例，不是唯一允许的关键词。
5. 没有合适分类或语义不足时返回空建议，界面显示“请选择分类”；不得编造分类、自动新建分类或用“默认”掩盖无法判断的结果。
6. 服务端校验请求列表结构及输出是否属于对应列表；每类去重后最多 128 个分类，每个名称最多 64 个 Unicode 字符。超过限制时明确提示调整分类后重试或手动填写，不静默截断用户分类；缺失列表使用默认列表，显式空列表表示该类没有可选分类。
7. 客户端再次校验当前分类；如果用户修改了分类列表或旧草稿建议已无效，保留其他草稿信息并要求重新选择分类。
8. 收入与支出分类隔离。旧客户端未提供列表时，API 使用当前产品默认收入/支出分类，保持接口兼容。

## 付款与承担状态

- 区分“付款方式未确认”“共同钱包”“某人垫付”三种状态。空付款人 ID 本身不能代表共同钱包已确认。
- 描述明确共同钱包时可预选共同钱包；明确某人付款且匹配有效时可预选垫付人；缺失或有歧义时显示“付款方式待确认”。
- 必须至少选择一位承担人并解决人员歧义，支出还需明确付款方式，才能确认保存。收入不展示付款方式选择。
- “共同钱包”与“某人垫付”只有一个统一选择区，不再重复展示两套互相矛盾的操作。
- 旧草稿没有新的付款状态信息时，空付款人视为待确认，有效付款人可恢复为垫付；不能把缺失信息默认解释为共同钱包。

## 金额展示

- 突出实际记账币种及总额；另一币种作为次要说明，明确“按账本汇率约合”，不是另一次支出，也不代表实时市场汇率。
- 未选择承担人时显示“请选择承担人”，不展示“0 人承担”或“每人 —”。
- 付款未确认时显示“付款方式待确认”，不展示共同钱包付款的确定结论。
- 人员和付款方式确认后显示紧凑摘要，例如“陈鑫垫付 · 3 人均分 · 每人 ¥10.00”。
- 保持现有均分业务语义，不在本次新增不等额分摊。金额计算沿用现有货币精度规则，不增加前端独立结算算法。
- 标签、提示和操作分开，窄屏不通过截断关键姓名或提示解决布局。沿用现有 Flutter 主题，不新增视觉框架。

## 数据流与组件边界

客户端读取分类 → API 鉴权并取得账本有效人员 → AI 生成受上下文约束的草稿 → API 校验分类与人员候选 → 客户端转换人员 UUID → 持久化可编辑草稿 → 用户确认 → 沿用现有幂等保存链路。

人员匹配、分类校验、同步身份转换和金额展示各自保持独立责任；不把所有新逻辑堆进 `AiDraftReview`。
草稿新增字段使用可选/版本兼容形式，覆盖队列序列化、恢复和修改持久化。
更新 AI 信息披露，说明本次请求会发送账本人员姓名和分类名称；不发送其他账本数据。

## 验收与测试

- 姓名：唯一同名、重复同名、唯一同音、近似字、多候选、无匹配、“我”无关联、删除人员、不同账号隔离。
- 身份：本地 UUID 与云端 UUID 不同仍正确选中，旧草稿可恢复，转换多次结果一致。
- 分类：早餐/午餐/晚餐/零食选餐饮，打车/地铁选交通，自定义分类可选，无合适分类待确认，非法分类被过滤，收入不能选支出分类，旧客户端兼容。
- 请求与队列：上下文正确传入，敏感资料不发送，AI 无效输出不保存，新增字段持久化和恢复完整，用户可覆盖建议。
- 页面：未确认人员/付款不展示确定分摊，已确认金额与换算层级清楚，窄屏和较大字体不截断关键内容，确认保存仍需必填校验。
- 用可控模拟响应验证语义契约和候选规则；真实模型语义效果单独验证，不能用模拟测试宣称已验证真实模型。
